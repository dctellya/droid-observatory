# Rule 13:43 widened, apply now: no process a worker launches reads the keychain, the app included

Source: pre-roci under the owner's delegation; triggered 15:18 by a second macOS keychain prompt, this time from `observatory-app` (the Tauri binary) launched by the worker of m4-gate-group-ui for its e2e run. The owner denied it. The 13:43 rule said "worker test"; the app's forge source reads `droid-observatory/github-token` at startup when `GITHUB_TOKEN` is unset, so the rule's words were too narrow. Blameless: the worker followed the rule as written.

1. The rule covers every process a worker starts: tests, the app under e2e, scripts, the browser host. None of them may reach the keychain. The keychain path exists only for the owner's own launch of the app from his terminal.
2. Mechanism, not a sentence: the e2e harness and every worker launch set `GITHUB_TOKEN` to a fake value of the right shape built at run time (as 0da61cb does for tests), or start the app with the forge source disabled in `config/observatory.toml` for the run. The app's `resolve_github_token` is never called with the keychain as the fallback unless an explicit owner flag (`FORGE_LIVE=1`) is set. Add a test: with `GITHUB_TOKEN` unset and `FORGE_LIVE` unset, the forge source is `off` and no keychain call is made.
3. A worker whose launched process prompts the owner's GUI records the row as owner-run and does not wait; if a prompt appeared, the live clause counts as not run whatever the answer.
4. Apply to the running worker at its next boundary and to m4-merge-ui-and-403, m4-forge-live-walk-2 and the M4 user-testing validator. Tool fact for library/tooling.md: macOS keychain ACL is per binary hash; a rebuilt app or test binary prompts again; "Always Allow" binds the secret to a throwaway build.

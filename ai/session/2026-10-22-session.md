## Entry 4 — Final design decisions before PRD draft

**Decisions (user, via questionnaire)**

**Lanes (exact, ordered):**

1. **Intent**: mission prompt, spec, acceptance criteria; later human re-prompts. Few events.
2. **Orchestrator**: plan, feature breakdown, milestones, task assignment, replans.
3. **Workers**: one sub-lane per worker (or per feature when the mission names them); events: task started, files touched, tests run, commits, task done.
4. **Validators, scrutiny**: review findings, blocking vs non-blocking, re-work requested.
5. **Validators, user testing**: QA runs against the built thing, scenario results.
6. **Integration**: worktree merges into the mission branch, conflicts, gate command runs ("integrated in mission", not "merged").
7. **Human**: approvals, answers to escalations, review of the outcome (the video), the merge of the PR.
8. **Outside**: GitHub PR opened, CI runs and attestations, deploys (ecosystem lane; empty for the observatory itself).
9. **Time, Waste, Cost and models**: tokens and usage per role, which model did what; doubles as budget meter; elapsed time, time stuck/wasted.

Every event carries session id, role, model, timestamp, duration, and a link to the raw JSONL line. **The lane is a view, not a copy.** Lanes 1–6 from the stream, 7–8 from GitHub and human actions, 9 from session metadata.

**Waste definition (user):**
- Active time: worker/validator/orchestrator doing something (tool call in flight, model generating).
- Waiting on human: question/approval open, nobody acting (lane 7 open, lanes 2–6 idle).
- Waiting on validation: work done, validator not started.
- Rework: time spent after a blocking finding on the same task.
- Retry and failure: tool errors, re-runs of same command, integration conflicts.
- **Waste = everything that is not active time on first-pass work**, split by cause, per feature and per role. Cost shown next to it (tokens × per-model multiplier) so slow-cheap vs fast-expensive models compare honestly.

**Gate (lane 8 + badge):** final lane holds the gate (PR opened → checks → merged); card badge shows gate state (pending, human required, policy-merged, CI green/red). **CI red reopens the mission**: new mission cycle on the same feature tagged `fix`, drawn as a loop back into Workers lane. Merge button appears only when policy says a human merges; otherwise badge flips to policy-merged automatically. A mission is complete when the gate is green and the merge happened, not when workers stop. Every red is a counted rework loop in lane 9.

**Card:** one card = one mission feature. Gate lane groups cards by the PR that carries them, badge on the group. A PR with three features shows three cards sharing one gate state. CI red loops back only to the card the fix touches.

**Cost:** tokens + Factory Standard Credits if the stream exposes them, else a price table. **Price table lives in a dated config file so every cost on the board names the prices it used.**

## Entry 6 — User review of PRD v0.1

**User review notes (verbatim)**

> # Review notes on droid-observatory-prd.md (22-oct-2026)
>
> Hints on the four points raised, plus one model correction that changes sections 7 and 12.
>
> ## 0. Delivery model (overrides my earlier "one milestone = one PR")
>
> - A **mission is a business feature: the unit that ships.** For this project, v1 of the observatory. One PR into `main` at the end, outcome-sized, with the evidence attached; the full attested CI runs on that PR; CD runs from `main`.
> - **Milestones are internal iterations**, not shippable. Each runs in its own worktree and is integrated into a `mission/<name>` branch, the mission's interface to `main`. Fast checks run on that branch (tests, lint, the gate command) to keep it healthy; nothing on it is shippable or pretends to be.
> - The mission branch is short-lived by construction: it dies at the merge. That is what keeps it from becoming git-flow's `dev`.
> - The board agrees with this: cards are milestones (the spec phases); the gate group is the mission's one PR; lane 6 is integration into `mission/<name>`; lane 8 is the PR. The fix loop after CI red reopens the mission on its branch; it does not open a new PR.
> - M0 (stream capture and mapping) is the first milestone of the same mission: the orchestrator captures a run and freezes the mapping before planning the rest. A manual 20-minute capture beforehand is optional insurance, not a structural step.
>
> ## 1. Section 6, event kinds to add
>
> - Lane 1 (Intent): `question.asked` (orchestrator to human), `intent.answered`, `spec.versioned`.
> - Lane 2 (Orchestrator): `milestone.completed`, `task.skipped`, `mission.paused`, `mission.resumed`, `mission.completed`, `context.compacted` (explains sudden quality drops).
> - Lane 3 (Workers): `subagent.spawned`, `subagent.finished`, `permission.requested`, `permission.granted`, `permission.denied`, `hook.blocked` (the write guard), `usage.reported` (feeds lane 9), `model.changed`.
> - Lane 4 (Scrutiny): `rework.resolved`, the closing event that bounds a rework window.
> - Lane 6 (Integration): `gate_command.passed` and `gate_command.failed`, not only `run`.
> - Lane 8 (Outside): `pr.review_requested`, `check.required_missing`, `ruleset.blocked`, `attestation.verified` (distinct from `attestation.recorded`).
> - Keep `unknown.event` as a first-class kind, counted and surfaced; M0's exit criterion is driving it to zero on the capture.
>
> ## 2. Section 9.2, metric definitions
>
> - **Rework** as written counts all active time after the first blocking signal, so legitimate new work after a fix reads as waste. Bound it: rework = active time between a blocking signal (`finding.blocking`, `qa.scenario.failed`, `integration.conflict`, `check.failed`) and its resolution event (`rework.resolved`, `qa.scenario.passed`, conflict resolved, `check.passed`), per signal. Overlapping windows merge.
> - **First-pass active time** = active time outside any rework window (not "before the first blocking signal").
> - **Mission overhead**: orchestrator time before `feature.defined` (and replanning time not attributable to one feature) belongs to no card. Report it separately, or apportion it explicitly; otherwise feature cycle times look shorter than the mission.
> - **Waiting on merge**: checks green, policy requires a human, nobody has merged. Add it as its own cause under waiting on human; it will be the largest waste bucket in practice.
> - **Cycle time** stops at `pr.merged` (human or policy) with CI green: correct for the gate.
> - **Idle** should distinguish "queued behind another feature" (WIP limit) from "nothing scheduled"; the first is a bottleneck signal, the second is not.
>
> ## 3. Section 11, stack
>
> - Tauri 2 + Leptos is defensible for the stated needs (markdown and video in Details, shared serde types, live board).
> - Two risks to name: Droids have far less Leptos than React or Svelte in their training, and the WASM/Trunk toolchain inside a Mission is a new failure mode. Mitigations already in the PRD are the right ones (core first, headless `observatory replay`, swap to TypeScript at the Tauri command boundary); make M1 the explicit go/no-go on Leptos, with the criterion written down (board renders replay in under N sessions of rework).
> - Update the model ids in the price-table example: `claude-sonnet-4-6` and `claude-opus-4-7` are old; current ids are `claude-fable-5-1`, `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-4-5-20251001`. Keep the table dated.
>
> ## 4. Section 12, milestones as the mission plan
>
> - The order M0 to M5 is right as the seed of the mission plan, under the delivery model in section 0: one mission, six milestones, one `mission/observatory-v1` branch, one PR at the end.
> - M0 must complete before the orchestrator plans M1 onward in detail: the stream schema is unknown until the capture exists. Plan the rest after M0, from the frozen mapping.
> - M4 (gate and fix loop) needs a repository with a PR flow, CI and rulesets to test against; use a private demo repository with CI rather than the observatory itself, which has no PR flow until the end of the mission.
> - M5's acceptance ("matches a hand-computed reference") needs the reference to exist: a spreadsheet computed by hand from the M0 capture, produced by the human once. Validators cannot invent that oracle.
> - Dogfooding from M1 holds: the mission that builds the observatory is observed in the observatory; its own lane 8 stays empty until the final PR.
